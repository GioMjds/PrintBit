# Microsoft Defender Upload Gate Design

## Goal

Prevent a customer from causing PrintBit to accept, parse, store, or print a malicious file that merely has an allowed document or image filename and header. The gate must work while the customer is in Microsoft Edge Assigned Access, without exposing a scanner UI or giving the kiosk account additional application access.

## Decision

PrintBit's Node backend runs from the existing machine-startup scheduled task as `SYSTEM`. It invokes the locally installed Microsoft Defender Antivirus command-line client, `MpCmdRun.exe`, to scan private staged uploads. The kiosk account runs only Assigned Access Edge; it neither starts nor interacts with Defender.

The scanner is fail closed. An upload is rejected when Defender is disabled, unavailable, returns an error, reports malware, times out, or has security intelligence older than seven days (168 hours).

## Threat model

Untrusted input enters through these surfaces:

- `POST /api/wireless/sessions/:sessionId/upload`
- `POST /upload` (legacy)
- `POST /api/report-issues/sessions/:sessionId/attachments`

An attacker can send a renamed executable, a malformed document, a PDF or OOXML polyglot, an archive/container designed to exhaust a parser, or content known to antivirus signatures. File extensions, request MIME types, and magic bytes are useful early filters but are not proof of safety.

The primary assets are the kiosk host, its print/scan/payment services, customer documents, and the availability of the machine. The boundary must therefore reject unsafe input before document analysis, conversion, printing, or final persistence.

## Architecture

### 1. Private bounded staging

Each upload is streamed by Multer to a server-owned staging directory outside any public/static route. The filename is generated by the server; the original filename is metadata only. The directory is writable by the backend task and is not writable or browseable by the Assigned Access user.

Staging has a per-file 25 MB limit, per-session byte limit, process-wide byte limit, and age/count cleanup. A failed or abandoned upload must be deleted or quarantined under the same retention policy. Multer memory storage is removed from all three upload surfaces so multipart bodies are not accumulated in the Node heap.

### 2. Validation and scan order

For each staged upload:

1. Enforce extension and declared-MIME allowlists; reject disguised executable names.
2. Inspect the actual bytes and validate OOXML internal structure where applicable.
3. Verify Defender health: Defender is active, its engine is reachable, and security intelligence is at most 168 hours old.
4. Run a custom Defender scan of the generated staging path with a fixed timeout and no shell interpolation.
5. On a clean result only, pass the file to the existing session, legacy, or report-attachment persistence path. The application must use the staged path/stream rather than reload the whole upload into memory.

`MpCmdRun.exe` is discovered only in Microsoft Defender's documented system locations. The backend calls it through `spawn`/`spawnFile` with an argument array; it never calls a shell and never passes a customer filename as an executable or command option.

### 3. Result handling

The scanner adapter reports one of `clean`, `infected`, `unavailable`, `stale`, `timeout`, or `failed`. Every result except `clean` blocks the request.

| Result                            | HTTP response          | Stored action                                                                                                                                   |
| --------------------------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `infected`                        | 422 `FILE_INFECTED`    | Move to bounded quarantine if Defender has not already remediated it; record a security event without returning scanner output to the customer. |
| `unavailable` or `stale`          | 503 `SCAN_UNAVAILABLE` | Remove private staging file; log the health reason.                                                                                             |
| `timeout` or `failed`             | 503 `SCAN_FAILED`      | Remove private staging file; log the failure reason.                                                                                            |
| invalid type or invalid structure | 422 `UNSUPPORTED_TYPE` | Move to bounded quarantine; do not scan or parse further.                                                                                       |

Security logs store the upload surface, generated file identifier, byte count, validation/scan result, and signature age. They do not store document contents, tokens, or full Defender command output. Quarantine records may store a malware family name when Defender provides one, but the customer receives only a generic rejection.

### 4. Kiosk and Assigned Access operation

The deployment uses the existing `scripts/install-startup.ps1 -AtStartup` task so the backend starts under `SYSTEM` before the kiosk user logs on. Assigned Access starts Edge separately at `/loading`. The scan happens in the backend's noninteractive session, so it produces no customer-visible application, dialog, taskbar item, or elevated prompt.

The installation/verification scripts must verify all of the following before deployment is accepted:

- the PrintBit startup task principal is `SYSTEM`;
- Microsoft Defender Antivirus is the active engine, not passive or disabled;
- the Defender command-line executable is available from an approved Microsoft system location;
- Defender security intelligence is no older than 168 hours;
- staging and quarantine ACLs deny the kiosk account and expose neither directory through static content;
- a clean file, a mismatched-header file, and the EICAR antivirus test file give the expected results while signed in as the Assigned Access account.

### 5. Interfaces

Production code receives a small `DefenderScanner` interface so tests can exercise the upload gate without invoking Windows Defender:

```ts
type DefenderScanStatus =
  | 'clean'
  | 'infected'
  | 'unavailable'
  | 'stale'
  | 'timeout'
  | 'failed';

interface DefenderHealth {
  readonly status:
    | Extract<DefenderScanStatus, 'unavailable' | 'stale'>
    | 'clean';
  readonly signatureAgeHours: number | null;
  readonly detail: string | null;
}

interface DefenderScanResult {
  readonly status: DefenderScanStatus;
  readonly detectionName: string | null;
  readonly detail: string | null;
}

interface DefenderScanner {
  getHealth(): Promise<DefenderHealth>;
  scanFile(stagedPath: string): Promise<DefenderScanResult>;
}
```

`PRINTBIT_DEFENDER_MAX_SIGNATURE_AGE_HOURS` defaults to `168`; invalid, zero, or negative values fail deployment verification rather than silently weakening the policy. `PRINTBIT_DEFENDER_SCAN_TIMEOUT_MS` has a conservative finite default and is bounded by configuration validation.

## Testing and acceptance

Unit and route tests must prove that all three upload surfaces reject scanner-unavailable, stale, failed, timed-out, and infected outcomes before their persistence or analysis services run, and accept a clean valid file. Tests also cover a renamed `MZ` executable, a valid-header file with invalid OOXML structure, and a scanner result that contains hostile-looking text so it cannot become a command or an unsafe log field.

Windows acceptance testing, conducted on a non-production kiosk, runs Defender against EICAR, verifies that the customer sees no system UI, and repeats the workflow under the Assigned Access kiosk account. The task is accepted only when the backend task remains `SYSTEM`, the kiosk account remains restricted to Edge, and every non-clean scanner outcome blocks upload.

## Scope boundary

This design restores the missing malware-scanning boundary and removes the memory-upload path that enabled the identified content-bypass risk. It does not close the other PB-FILE-001 items by itself: vulnerable runtime dependencies, CSP/security headers, converter sandboxing, CPU/output limits, and a full quarantine-retention service need subsequent, separately reviewed slices. The production audit must remain open until those controls have their own verified evidence.
